I had an API taking almost 4 seconds to respond.
The strange part?
CPU was sitting around 40%.
So why was the API slow?

🔍 The first clue
The service wasn’t busy computing.
It was waiting.
That changed how we approached the investigation.
Instead of looking at algorithms, we started looking at what the request was waiting for.

What the endpoint was doing
The code looked completely normal:
→ Fetch a list of entities
→ Loop over them
→ Build DTOs
Nothing suspicious at first.
Until we looked inside the loop.

⚠️ Two expensive things were happening
For every item:
→ A lazy relation was being accessed → another DB query
→ A synchronous HTTP call was made to another service
And the external call was averaging around 350ms.
With 15 items:
15 × 350ms = 5.25 seconds
That’s potentially more than 5 seconds of sequential network waiting.
But the network call wasn’t the biggest problem.

💥 The real problem
The request was running inside an open transaction.
Which meant it was holding a database connection while waiting for the network.
The database wasn’t doing anything.
The application wasn’t doing much either.
But the connection was still occupied.

Then concurrency made it worse
Imagine a connection pool with 10 connections.
10 concurrent requests arrive.
→ 10 connections occupied
→ Each request waits on network I/O
→ The pool is exhausted
→ New requests start waiting
→ The queue grows
→ Eventually, requests time out
The service looks overloaded.
But it isn’t actually CPU-bound.
It’s blocked.

💡 This is why metrics matter
High CPU + high latency?
The application may be doing too much work.
Low CPU + high latency?
The application may be waiting.
That distinction can completely change where you investigate.

The fixes
We didn’t need a clever algorithm.
We needed to remove the unnecessary waiting:
→ Fetch relations explicitly with JOIN FETCH or an EntityGraph
→ Batch external calls instead of making them inside the loop
→ Move network I/O outside the transaction boundary
→ Centralize exception handling so failures remain consistent
→ Cache read-heavy paths when a little staleness is acceptable

🎯 The lesson
Never hold a database connection while waiting on the network.
This kind of bug is dangerous because the code can look perfectly reasonable during review.
Tests pass.
Everything works with three seeded records.
Then production brings:
More data. More concurrency. More network latency.
And suddenly…
the same code behaves completely differently.
Sometimes an application is slow precisely because…
it’s doing nothing.

System Design Patterns Simplified

Understanding system design patterns is essential for building reliable, scalable systems. Here’s a simplified breakdown with real-world analogies.

1. Failure Handling Patterns
Handle service crashes and recovery smartly.
- Circuit Breaker: Stops calling failing services to prevent bigger failures.
- Retry Pattern: Automatically retries failed requests after a delay.
- Timeout Pattern: Stops waiting after a set time to avoid blocking.

2. Traffic & Load Control
Avoid overloading your systems under high demand.
- Rate Limiter: Controls request frequency to prevent system overload.
- Bulkhead: Isolates failures to prevent cascading issues.

3. Caching Patterns
Improve speed and performance using smart data caching.
- Cache Aside: Loads data into cache only when needed.
- Write-Through Cache: Updates cache and database together for consistency.

4. Messaging & State Tracking
Ensure smooth communication and traceable actions.
- Publish-Subscribe: Sends messages to multiple listeners asynchronously.
- Event Sourcing: Logs events to recreate system state later.

5. Architecture & Data Flow
Make systems scalable, maintainable, and modular.
- CQRS: Splits reads and writes for performance.
- Strangler Fig: Gradually replaces legacy code without full rewrites.
- Saga Pattern: Manages multi-step transactions with rollback support.

Most explanations of Java Virtual Threads stop at:
“Virtual Threads are lightweight threads.”
That barely explains what actually changed inside the JVM.

Traditional Java threads follow:
𝟭 𝗝𝗮𝘃𝗮 𝗧𝗵𝗿𝗲𝗮𝗱 = 𝟭 𝗢𝗦 𝗧𝗵𝗿𝗲𝗮𝗱
Each platform thread gets:
▸ native stack memory
▸ kernel scheduling
▸ dedicated OS resources
Which makes threads expensive.

A single platform thread may reserve ~1 MB stack memory.
So:
100k requests -> 100k platform threads
can quickly create:
▸ memory pressure
▸ context switching overhead
▸ scheduler contention

𝗩𝗶𝗿𝘁𝘂𝗮𝗹 𝗧𝗵𝗿𝗲𝗮𝗱𝘀 𝗰𝗼𝗺𝗽𝗹𝗲𝘁𝗲𝗹𝘆 𝗰𝗵𝗮𝗻𝗴𝗲 𝘁𝗵𝗶𝘀 𝗺𝗼𝗱𝗲𝗹.
Internally:
𝙈𝙖𝙣𝙮 𝙑𝙞𝙧𝙩𝙪𝙖𝙡 𝙏𝙝𝙧𝙚𝙖𝙙𝙨
    ↓
𝙁𝙚𝙬 𝘾𝙖𝙧𝙧𝙞𝙚𝙧 𝙏𝙝𝙧𝙚𝙖𝙙𝙨 (𝙊𝙎 𝙏𝙝𝙧𝙚𝙖𝙙𝙨)
But Virtual Threads are NOT just “smaller threads”.
They are implemented using 𝘾𝙤𝙣𝙩𝙞𝙣𝙪𝙖𝙩𝙞𝙤𝙣𝙨.
𝘈 𝘤𝘰𝘯𝘵𝘪𝘯𝘶𝘢𝘵𝘪𝘰𝘯 𝘪𝘴 𝘦𝘴𝘴𝘦𝘯𝘵𝘪𝘢𝘭𝘭𝘺:
𝘈 𝘱𝘢𝘶𝘴𝘦𝘥 𝘤𝘰𝘮𝘱𝘶𝘵𝘢𝘵𝘪𝘰𝘯 𝘵𝘩𝘢𝘵 𝘤𝘢𝘯 𝘳𝘦𝘴𝘶𝘮𝘦 𝘭𝘢𝘵𝘦𝘳
When a Virtual Thread blocks on:
▸ database calls
▸ HTTP requests
▸ socket I/O
▸ sleep()
the JVM:
captures thread state
stores stack frames into heap-based stack chunks
unmounts the Virtual Thread
releases the carrier thread

So:
𝘽𝙡𝙤𝙘𝙠𝙚𝙙 𝙧𝙚𝙦𝙪𝙚𝙨𝙩 != 𝘽𝙡𝙤𝙘𝙠𝙚𝙙 𝙊𝙎 𝙩𝙝𝙧𝙚𝙖𝙙
This is the core scalability breakthrough of Project Loom.

𝗔𝗻𝗼𝘁𝗵𝗲𝗿 𝗺𝗮𝗷𝗼𝗿 𝗱𝗶𝗳𝗳𝗲𝗿𝗲𝗻𝗰𝗲:
𝘗𝘭𝘢𝘵𝘧𝘰𝘳𝘮 𝘵𝘩𝘳𝘦𝘢𝘥 𝘴𝘵𝘢𝘤𝘬𝘴: 𝘊𝘰𝘯𝘵𝘪𝘨𝘶𝘰𝘶𝘴 𝘯𝘢𝘵𝘪𝘷𝘦 𝘮𝘦𝘮𝘰𝘳𝘺
𝘝𝘪𝘳𝘵𝘶𝘢𝘭 𝘵𝘩𝘳𝘦𝘢𝘥 𝘴𝘵𝘢𝘤𝘬𝘴: 𝘏𝘦𝘢𝘱-𝘣𝘢𝘴𝘦𝘥 𝘴𝘵𝘢𝘤𝘬 𝘤𝘩𝘶𝘯𝘬𝘴
This allows millions of waiting threads with far lower memory overhead.

In Java 21–23, blocking inside synchronized sections could pin carrier threads.
Java 24 fixed most of this via JEP 491 by making JVM monitors virtual-thread aware.
Now, in most synchronized blocking scenarios:
▸ Virtual Threads can unmount
▸ carrier threads can be reused
▸ scalability is preserved
Some pinning scenarios still exist:
* JNI/native calls
* foreign function boundaries

because native execution cannot always be safely suspended.
Also:
Virtual Threads do NOT improve CPU-bound performance.

They primarily optimize:
▸ blocking workloads
▸ concurrency efficiency
▸ memory usage
▸ scalability

𝗧𝗵𝗲 𝗳𝗮𝘀𝗰𝗶𝗻𝗮𝘁𝗶𝗻𝗴 𝗽𝗮𝗿𝘁 𝗶𝘀:
developers still write simple blocking code while the JVM transparently handles suspension, scheduling, continuation capture, and remounting underneath.


Spring Boot & Hibernate: Understanding the N+1 Problem in Simple Words
Have you ever wondered why your Spring Boot API is slow even when your SQL query looks simple?
One possible reason is the N+1 Query Problem in Hibernate.
Let’s understand it with a real-world example. 👇

👨‍💻 1. Imagine You Have 500 Employees
Suppose your application has two database tables:

📌 Employee table
Employee ID
Employee Name
Department ID

📌 Department table
Department ID
Department Name

Now, you want to display all employees along with their department names.
Sounds simple, right?

But Hibernate might execute 501 SQL queries to get this information!
🤔 2. Why Does This Happen?
First, Hibernate fetches all 500 employees using one query:
SELECT * FROM employee;
Then, when your code accesses each employee's department, Hibernate may execute another query to fetch that department.
SELECT * FROM department WHERE id = 1;
SELECT * FROM department WHERE id = 2;
SELECT * FROM department WHERE id = 3;
This continues for the departments that haven't already been loaded.
So, in the worst-case example:
✅ 1 query to fetch employees
❌ 500 additional queries to fetch departments
Total = 501 database queries!
This is called the N+1 Problem.
Here, N represents the number of employees, and 1 represents the initial query.
⚠️ If multiple employees belong to the same department, Hibernate may execute fewer additional queries.

💡 3. How Can We Identify This Problem?
Sometimes, the API returns the correct data, but it takes too long to respond.
Here are a few warning signs:
🔹 Your application executes hundreds of SQL queries for one API request.
🔹 Similar SQL queries run repeatedly with different IDs.
🔹 The API becomes slower as the number of records increases.
🔹 Your database receives more requests than expected.
You can enable Hibernate SQL logging in your local development environment:
spring.jpa.show-sql=true
logging.level.org.hibernate.SQL=DEBUG
This helps you see which SQL queries Hibernate is executing.

🛠️ 4. How Can We Fix the N+1 Problem?
One common solution is JOIN FETCH.
Instead of fetching employees first and then fetching their departments separately, we ask Hibernate to fetch both together.
Example:
@Query("""
    SELECT e
    FROM Employee e
    JOIN FETCH e.department
    """)
List<Employee> findAllWithDepartment();
Now, Hibernate can fetch employees and their departments in a single SQL query.
Instead of making hundreds of database calls, we reduce unnecessary database round trips.
Another option is @EntityGraph, which lets us specify which relationships should be fetched for a particular query.
Batch fetching is also useful when we want Hibernate to load related data in groups instead of one at a time.
✅ The best solution depends on the data we need and how our application uses it.
📈 5. What Are the Benefits?
✅ Reduce unnecessary database queries
✅ Improve API response time
✅ Handle increasing data volumes more efficiently


Java 21 Virtual Threads: Handle More Requests with Less Waiting!

Imagine your Spring Boot API receives 1,000 requests at the same time. What happens when most of them are waiting for a database response?

With traditional thread pools, available threads can become occupied while waiting for I/O operations.

This is where Virtual Threads make a difference! 💡

🔹 Traditional Thread Pool

- Limited number of threads
- Incoming requests may wait in a queue
- Threads can remain blocked during database calls

🔹 Virtual Threads (Java 21)

- Lightweight threads make it practical to handle many concurrent tasks
- While waiting for I/O, a virtual thread can unmount, allowing its carrier thread to run other work
- Helps improve throughput for I/O-heavy applications

⚡ How to enable them in Spring Boot 3.2+:

spring.threads.virtual.enabled=true

3 things to remember:

✅ Virtual threads improve concurrency, not the speed of every individual request.

✅ Use one virtual thread per task instead of pooling virtual threads.

✅ Watch out for long blocking operations inside "synchronized" sections and other resource bottlenecks.

🎯 The takeaway: Virtual threads can help your Java applications serve more concurrent requests without needing a huge pool of platform threads.


 Spring Boot Interview Question: What Is the Difference Between `@Component`, `@Service`, `@Repository`, and `@Controller`?

All four annotations help Spring manage beans, but they serve different purposes in your application.

Let's break them down with a real-world example! 👇

🔹 1. `@Component` — The General-Purpose Bean

The most generic stereotype annotation.

Use it when a class needs to be managed by Spring but doesn't fit a more specific role.

```java
@Component
public class EmailValidator {
    public boolean isValid(String email) {
        return email != null && email.contains("@");
    }
}
```

📌 Use case: Validators, helpers, and utility components.

🔹 2. `@Service` — The Business Logic Layer

Used to identify classes that contain business logic.

```java
@Service
public class UserService {
    public String getWelcomeMessage() {
        return "Welcome to Spring Boot!";
    }
}
```

📌 Use case: Business rules, workflows, and coordination between repositories and other services.

🔹 3. `@Repository` — The Data Access Layer

Used for classes responsible for database access.

```java
@Repository
public class UserRepository {
    // Database access logic
}
```

📌 Important: `@Repository` also participates in Spring's persistence exception translation, converting supported persistence exceptions into Spring's `DataAccessException` hierarchy when the relevant infrastructure is configured.

With Spring Data JPA, repository interfaces are typically discovered and implemented automatically — you usually don't need to write a concrete class with `@Repository`.

🔹 4. `@Controller` — The Web Layer

Used to handle web requests, commonly in Spring MVC applications.

```java
@Controller
public class PageController {
    @GetMapping("/home")
    public String home() {
        return "home";
    }
}
```

📌 Use case: Returning views such as Thymeleaf templates.

For REST APIs, we commonly use `@RestController`.

🔹 5. Bonus: `@RestController` — For REST APIs

`@RestController` combines `@Controller` and `@ResponseBody`.

```java
@RestController
@RequestMapping("/api/users")
public class UserController {

    @GetMapping("/{id}")
    public String getUser(@PathVariable Long id) {
        return "User ID: " + id;
    }
}
```

The return value is written directly to the HTTP response body rather than being interpreted as a view name.

🎯 Quick Comparison

✅ `@Component` → General-purpose Spring bean

✅ `@Service` → Business logic

✅ `@Repository` → Data access

✅ `@Controller` → Web MVC and view handling

✅ `@RestController` → REST API responses

How do you maintain data consistency when one business transaction spans multiple microservices? 🔥

Imagine an e-commerce checkout involving four services:

1. Order Service creates an order.
2. Payment Service processes the payment.
3. Inventory Service reserves the products.
4. Shipping Service creates a shipment.

Each service owns its own database. A single ACID transaction usually cannot cover the entire workflow across independent services.

This is where the Saga Pattern becomes useful.

🔄 How does Saga work?

A Saga breaks a distributed business transaction into a sequence of local transactions. Each step commits independently.

Successful flow:

Create Order → Process Payment → Reserve Inventory → Create Shipment → ✅ Order Completed

What happens if inventory reservation fails after payment succeeds?

The system executes compensating actions:

❌ Inventory reservation fails
↩️ Refund Payment
↩️ Cancel Order
🔔 Notify the customer about the failure

These compensations are business operations, not automatic database rollbacks. They may also fail, so they need their own retry and recovery strategy.

Two ways to implement Saga

1. Choreography

- Services react to events published by other services.
- Fewer centralized coordination dependencies.
- Can become difficult to trace as workflows grow.

2. Orchestration

- A Saga orchestrator controls the sequence of steps.
- Makes workflow state and recovery logic more explicit.
- Adds a coordinator that must be designed and operated reliably.

Senior backend engineering practices

✅ Persist Saga state so workflows can recover after crashes.

✅ Make commands, consumers, and compensating actions idempotent.

✅ Use durable messaging and handle duplicate or out-of-order events.

✅ Define timeouts and bounded retry policies for each step.

✅ Track a correlation ID or Saga ID across services.

✅ Monitor stuck workflows and failed compensations.

✅ Build reconciliation and manual recovery paths for cases that automation cannot resolve.

Common mistakes

❌ Assuming Saga provides global ACID atomicity.

❌ Implementing forward actions without designing compensations.

❌ Assuming a refund or cancellation always succeeds immediately.

❌ Retrying forever without tracking workflow state.

❌ Ignoring partial completion and eventual consistency.

The key principle: A Saga does not make a distributed transaction atomic. It makes its failure and recovery paths explicit.

Use Saga for long-running business workflows across independently owned services. For a transaction contained within one database, a normal database transaction is usually simpler.

Spring Boot + OpenFeign: Your API Call Failed. Will It Retry Automatically?

Imagine you're building a microservices application.

Your Order Service calls your Customer Service using Feign Client.

Everything works perfectly… until the Customer Service temporarily becomes unavailable. 😶

Here's an important question:

👉 Will Feign automatically retry the failed request?

Not by default in Spring Cloud OpenFeign!

Spring Cloud OpenFeign configures "Retryer.NEVER_RETRY" by default. This differs from the default retry behaviour of core Feign.

Let's understand how to configure a retry strategy. 👇

💻 Step 1: Create a custom retry configuration

@Configuration
public class FeignRetryConfig {

    @Bean
    public Retryer retryer() {
        return new Retryer.Default(
            200,   // Initial retry interval (ms)
            1000,  // Maximum retry interval (ms)
            3      // Maximum attempts
        );
    }
}

💻 Step 2: Apply it to your Feign Client

@FeignClient(
    name = "customer-service",
    url = "${customer.service.url}",
    configuration = FeignRetryConfig.class
)
public interface CustomerClient {

    @GetMapping("/customers/{id}")
    Customer getCustomer(
        @PathVariable("id") Long id
    );
}

💡 But here's the catch!

Configuring a Retryer does NOT mean every failed HTTP request will be retried.

Feign retries only when the failure is represented by an appropriate retryable exception.

For example, an HTTP 500 response isn't automatically retryable under the default error-decoding behaviour.

Before enabling retries in production, consider:

✅ Transient failures: Is the problem temporary?

✅ Timeouts: How long should we wait for a response?

✅ Idempotency: Could retrying create duplicate orders or payments?

✅ Circuit breakers: Should we stop calling a service that is consistently failing?

✅ Retry limits: Could repeated attempts make an overloaded service even worse?

🔥 My biggest takeaway:

Feign Client simplifies communication between microservices, but reliable communication requires more than simply adding "@FeignClient".

Understanding what happens when things fail is just as important as understanding how things work when everything is successful.

Adding @Async to a method seems like magic. You call the method, your API responds instantly, and the work happens in the background.
It works great on your machine with 5 test requests.
Then comes production traffic. Thousands of users hit your endpoint, and your application suddenly crashes with:
 java.lang.OutOfMemoryError: unable to create new native thread
What went wrong?
1. The Default Executor Has No Ceiling If you don't define a thread pool, Spring uses SimpleAsyncTaskExecutor. Despite the name, it is not a pool. It does not reuse existing threads. Instead, it spins up a brand-new operating system thread for every single @Async call. 1,000 requests = 1,000 new OS threads. Your server runs out of memory, and the JVM crashes.
2. The Invisible "Same-Class" Trap Just like @Transactional, @Async relies on Spring proxies. If you call an @Async method from inside the same service class (this.sendEmail()), the proxy is bypassed. It executes synchronously on the main thread, blocking your user without showing any error.
3. The Safe Fix: Bounded Thread Pools Always declare a custom ThreadPoolTaskExecutor:
 • Core Size: The steady team of worker threads (e.g., 10).
 • Queue Capacity: The waiting room when workers are busy (e.g., 100).
 • Max Size: Extra workers to hire during traffic spikes (e.g., 50).
 • Rejection Policy: What to do when the waiting room is full (e.g., CallerRunsPolicy to slow down the caller instead of crashing).

 JAVA API SERIES #05 — Comparable vs Comparator

🚀 Same Goal. Different Strategies. Do You Know When to Use Each? 👀

Sorting objects in Java seems simple.

Until you need to decide HOW they should be sorted.

That's where Comparable and Comparator come in.

🔵 1. COMPARABLE — Natural Ordering

Defines the natural ordering of objects within the class itself.

✅ Implements Comparable<T>
✅ Uses compareTo()
✅ Defines a natural ordering
✅ Useful when one default ordering makes sense

Example: Sorting employees by ID or dates chronologically.

🟢 2. COMPARATOR — Custom Ordering

Defines an external comparison strategy without modifying the class.

✅ Implements Comparator<T>
✅ Uses compare()
✅ Supports multiple sorting strategies
✅ Works with lambdas and method references

Example: Sorting employees by salary, name or experience.

⚡ THE KEY DIFFERENCE

🔵 Comparable → HOW objects naturally compare.
🟢 Comparator → HOW you choose to compare them.
💡 REAL-WORLD EXAMPLE

Imagine a banking application managing transactions.

You might need to sort transactions by:

📅 Date → Chronological order
💰 Amount → Highest value first
🏦 Account → Grouped by account identifier

Instead of forcing every sorting rule into the domain object, you can use different Comparators for different business needs.

🏗️ THE ENGINEERING LESSON

Good design isn't just about making code work.

It's about choosing solutions that are flexible, readable and easy to maintain.

And remember:

⚠️ When using TreeSet or TreeMap, comparison results also determine which elements or keys are considered equivalent.

A poorly designed comparison strategy can cause unexpected behavior.

🎯 Comparable defines the default. Comparator gives you flexibility.

6 Retry and Resilience Mechanism every software engineer must know 🧑🏻‍💻💯

You can learn these techniques for free at intervueclub.com. Lets proceed.

Every service fails at some point. What matters is how our system handles it.

Here are 6 patterns that keep systems running when things break:


1. Timeout
Don't wait forever. If a call takes too long, give up and move on.

2. Retry
Many failures are temporary, so try again.

3. Exponential backoff
Wait 1s, then 2s, then 4s, then 8s. This gives the service time to recover.

4. Jitter
Add a small random delay. Otherwise thousands of clients retry at the exact same moment and knock the service down again.

5. Circuit breaker
If a service keeps failing, stop calling it for a while. Fail fast, then test it again later.

6. Fallback
When all else fails, return something useful, like cached data or a default response.

These work best together. Retries without backoff and jitter can turn a small outage into a big one.
